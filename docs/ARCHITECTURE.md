# Architecture

Reference for the Buy or Wait? financial decision agent. Every number and name below is taken from
the code or from the final run's artifacts, not from intent. `README.md` is the entry point for
running the system; `code/DESIGN_NOTES.md` records why each decision was made and what was
rejected. This document describes what the system *is*.

---

## 1. Shape of the system

A deterministic financial core, wrapped by an agent. Structured data flows through typed loaders
into a reconstruction that produces dated cash flows. Unstructured evidence (215 messages, 16
document images) is turned into typed facts by a model and applied to those flows under fixed
rules. The simulator, planner and verifier are pure functions of the result. The model sits on top
as an orchestrator: it calls tools, checks that evidence and forecast agree, chooses among verified
candidates and writes a rationale. An arbiter re-applies the ranking rule after it submits.

The division is deliberate and is the central design decision: **no value written to `output.csv`
is generated by a language model.** The model classifies text, reads amounts off images, and picks
among candidate plans the deterministic core has already proved safe.

```
dataset/*.csv ─┐
               ├─► data.py (typed load, joins validated)
dataset/media ─┘        │
                        ▼
messages, images ─► evidence.py ─► typed Fact objects ─► state.py ─► forecast.py
                     (Nova Pro,        18 types,          dated       90-day
                      Qwen3-VL,        8 cash-affecting   cash flows  simulation
                      regex fallback)                                     │
                                                                          ▼
                                       verify.py ◄─ explain.py ◄─ planner.py
                                            │                     candidates + ranking
                                            ▼
                          agent.py (tool loop) ─► arbiter ─► output.csv
                                                              runs/audit.jsonl
                                                              evaluation/usage_report.md
```

## 3. The trust boundary

Messages and images are untrusted input. The only path from them into the forecast is a closed
schema of 18 fact types, of which just 8 may move money:

```
salary_amount_change   salary_date_change   salary_confirmed   income_ended
invoice_approved       one_time_credit_confirmed               rent_increase_pct
blank_amount_resolved
```

Anything a message says that does not map to one of those has no representation and therefore no
effect. The corpus contains one prompt-injection-shaped message, a prize-release-fee solicitation;
it maps to `scam_solicitation`, which is not cash-affecting. This is a structural guarantee, not a
filter that must catch every phrasing.

Both extraction prompts and the agent system prompt state that embedded instructions are ignored.

## 4. Reconstruction rules

`state.py` turns the ledger plus facts into dated flows.

| Flow | Rule |
|---|---|
| Known future rows | Scheduled and pending rows on their settlement date; pending debits reserved at the request date. Cancelled, failed, unrealized and non-cash rows are dropped. |
| Pending credits | Never counted until they settle. |
| Recurring income | Payroll-type descriptions only. Needs two occurrences, or a scheduled row, a same-period twin, or a confirming message. Stale after 45 days. Stopped by a final payroll or an `income_ended` fact. |
| Fixed commitments | Per description, on the observed cadence; a row dated on the request date is still owed. |
| Variable spending | Per category (`groceries, transport, dining, shopping, entertainment`) on the observed cadence; a row dated on the request date is not projected. |
| Budget | `minimum_allowed_amount / ratio` where a ratio is known (0.5 dining, entertainment, gym, streaming; 0.4 shopping), else the history mean. |
| Currency | Converted at the settlement-date rate; every fallback is recorded in the audit. |

`Policy` exposes twelve settings. The shipped defaults, selected over a 72-configuration grid and
cross-validated, are `budget_method="mean"`, `cadence_mode="mean"`, `variable_model="discrete"`,
`capacity_horizon="capacity_only"`, `debits_before_credits=False`, `stale_income_days=45`,
`min_occurrences=2`, `variable_window_days=180`.

## 5. Forecast and capacity

`amount_safe_to_pay` is the projected trough minus `minimum_balance_to_keep`, clamped to
`[0, requested_amount]`. `earliest_date_for_full_payment` is the first day whose suffix-minimum
balance still clears the minimum after the full amount.

Both are measured to the last projected income date inside the horizon rather than to the raw
90-day cut (`Reconstruction.safety_end`, `capacity_horizon="capacity_only"`). The 90-day window
ends at an arbitrary point in a user's pay cycle; when it lands after the last income, the tail is
a partial month of pure outflow whose next salary falls outside the window. **Recommended plans are
still validated across the full 90 days**, which is what the specification requires.

## 6. Planning and ranking

Candidates: full payment today, each supplied installment option, a two-payment partial, waiting
for the earliest safe date, and each of those with a spending-change set. Each is simulated in its
own counterfactual forecast and carries a `Proof` recording validity, lowest projected balance and
first breach date.

Eligibility is hard, not a preference: a method must appear in `payment_methods_user_will_consider`;
an installment option must not exceed `max_installment_months`, must not start before the request
date, and must finish by `desired_completion_date`; its schedule is followed exactly and never
shifted. Spending changes are limited to three, one per series, only on non-protected flexible
series in a category the user permits, `reduce_to` never below `minimum_allowed_amount`, and stop
and reduce never on the same event.

Surviving plans are ranked by the specification's own six keys, in order: completes by the deadline,
needs no spending changes, lowest total paid, earlier first payment, fewer payments, lowest option
id. This is a lexicographic total order, so sorting yields the unique optimum.

## 7. Agent loop and arbiter

`agent.py` runs a Bedrock Converse tool loop, at most `MAX_TURNS = 6`, with three tools:

| Tool | Purpose |
|---|---|
| `analyze_request` | Reconstruct, forecast, and return every candidate with its safety verdict, the rejected options with reasons, and the arbiter's own ranking |
| `inspect_flows` | The projected cash flows up to the trough, when evidence and forecast appear to disagree |
| `submit_decision` | A `candidate_id` the tools returned, plus a rationale |

The model may only name a candidate the tools produced. After it submits, the arbiter re-applies
the ranking; a differing choice is recorded in the audit and does not change the row. On the final
run the model agreed with the arbiter on 244 of 250 requests, averaging 2.0 turns, with zero
provider fallbacks.

## 8. Verification, in layers

1. `verify.py` re-checks every rendered row against the submission contract.
2. `explain.check_consistency` rejects an explanation whose numbers disagree with its row.
3. `pipeline.decide_request` self-repairs: if the top-ranked plan fails verification it emits the
   next ranked plan rather than an invalid row. It has never fired on this dataset.
4. `evaluation/audit.py` walks the specification over the produced file: 37 checks, zero failures.
5. `evaluation/requirements_check.py` proves each stated requirement: 14 pass.
6. `code/tests/`: 47 tests, of which 23 are metamorphic invariants that must hold for every input.

## 9. Degradation

Provider errors are classified. Access denied, expired session, missing dependency and unknown
model stop retries immediately; throttling and timeouts retry three times with backoff. After that
the request takes the deterministic path and the run summary counts the fallback. `--mode
deterministic` produces a fully valid `output.csv` with no credentials at all; only the agent
rationale is lost. Unresolved blank amounts are excluded with a note, never treated as zero.
